# 1Line OS - Concurrency, Optimistic Locking & Collision Prevention (نظام قفل التزامن ومنع تضارب التعديلات)

## نظرة عامة
في بيئة العمل العقارية متعددة الفرق (مبيعات، مخزون، عمليات، متابعة)، قد يقوم أكثر من موظف بفتح نفس العميل أو نفس العقار أو محاولة استلام نفس الطلب الوارد في أجزاء من الثانية. بدون حماية حازمة، تتسبب هذه العمليات في:
1. **فقدان التعديلات (Lost Updates):** قيام مستخدم بحفظ بيانات قديمة تمسح تعديلات أحدث حفظها زميله.
2. **الاستلام المزدوج (Dual Claim):** محاولة مندوبين التواصل مع نفس العميل مما يسبب تشتتاً للعميل.
3. **الحجز المزدوج (Double-Booking):** قيام مستشارين ببيع أو حجز نفس الوحدة العقارية لمشترين مختلفين.

يقدم **1Line OS** في الخطوة **5.6** معمارية ثلاثية الطبقات لحل هذه المشكلات جذرياً.

## 1. القفل المتفائل وتتبع الإصدارات (Optimistic Locking & Versioning)

- يحمل كل سجل (`Lead`, `Property`, `Deal`) حقلاً للإصدار `version: number`.
- عند حفظ أي تعديل، يتم إرسال النسخة المتوقعة (`expectedVersion`).
- يقوم محرك [`src/services/concurrencyEngine.js`](file:///e:/New%20folder/Local%20Disk/Business/%D8%A8%D8%B1%D9%85%D8%AC%D9%87/%D9%85%D9%88%D9%82%D8%B9/src/services/concurrencyEngine.js) بفحص النسخة:
  - **إذا تطابقت النسخة:** يُقبل التعديل وتتم زيادة رقم الإصدار تلقائياً بمقدار 1 (`nextVersion = version + 1`)، مع تسجيل اسم ومعرف آخر محرر وتوقيت الحفظ.
  - **إذا اختلفت النسخة:** يُرفض الحفظ فوراً بخطأ `version_conflict`، وتفتح تلقائياً نافذة حل التضارب [`ConcurrencyConflictModal.jsx`](file:///e:/New%20folder/Local%20Disk/Business/%D8%A8%D8%B1%D9%85%D8%AC%D9%87/%D9%85%D9%88%D9%82%D8%B9/src/components/crm/ConcurrencyConflictModal.jsx).

```javascript
import { validateOptimisticUpdate } from './src/services/concurrencyEngine.js';

const result = validateOptimisticUpdate(currentLead, updates, expectedVersion, currentUser);
if (result.conflict) {
  // إظهار نافذة التضارب للمستخدم مع خيارات إعادة التحميل
}
```

## 2. القفل المؤقت ومؤشر التواجد الحي (Pessimistic Soft Lease & Active Presence)

- عند فتح مستشار المبيعات لدرج العميل أو نافذة العقار، يتم حجز قفل مؤقت (Lease) مدته **3 دقائق**:
  ```json
  "activeEditor": {
    "uid": "user_123",
    "name": "أحمد رضوان",
    "role": "sales_agent",
    "lockedAt": "2026-10-15T12:00:00Z",
    "expiresAt": "2026-10-15T12:03:00Z"
  }
  ```
- **نبضات التجديد (Heartbeat):** طالما النافذة مفتوحة لدى الموظف، يرسل المتصفح نبضة تجديد كل 60 ثانية لمد صلاحية القفل.
- **تنبيه التواجد للزملاء:** إذا فتح زميل آخر نفس العميل، تظهر له شارة تحذيرية حية [`ActiveEditorBanner.jsx`](file:///e:/New%20folder/Local%20Disk/Business/%D8%A8%D8%B1%D9%85%D8%AC%D9%87/%D9%85%D9%88%D9%82%D8%B9/src/components/crm/ActiveEditorBanner.jsx):
  > 🔒 **هذا السجل قيد التعديل حالياً بواسطة "أحمد رضوان"** (قفل مؤقت لمنع التضارب - متبقي 2:15 دقيقة)
- **صلاحية كسر القفل (Admin Force Unlock):** يمتلك مدير النظام (`super_admin`) زراً فورياً لفك القفل بالقوة في حالات الطوارئ.

## 3. الاستلام الذري المتزامن (Atomic Claim via Transactions)

- **القاعدة الذهبية:** الاستلام عبر معاملة ذرية في Firestore (`runTransaction`) تضمن أنه في حال ضغط موظفان زر "استلمت الطلب" في نفس اللحظة:
  - ينجح الأول فقط.
  - يفشل الثاني فوراً برسالة ودية: *"تم استلام هذا الطلب بالفعل بواسطة زميلك [الاسم]"*.
- **قاعدة "الاستلام ≠ تواصل":** عملية الاستلام تُعين مسؤول المتابعة وتسجل توقيت الاستلام `assignedAt`، ولكنها **تحتفظ بحالة العميل `new` تماماً** دون تحويلها إلى `contacted` حتى يقوم الموظف بمكالمة العميل وتوثيق نتيجتها فعلياً.

## 4. منع الحجز المزدوج للوحدات (Property Double-Booking Protection)

- في حال حاول اثنان من المستشارين حجز نفس الوحدة العقارية أو تسجيل عربون عليها:
- تفحص دالة `validatePropertyBooking`:
  - إذا كانت الوحدة `reserved` أو `deposit_paid` أو `sold`، يُمنع الحجز الثاني قطعياً.
  - تُرجع الدالة رسالة تفصيلية: *"تنبيه حازم لمنع البيع المزدوج: هذه الوحدة محجوزة بالفعل بحالة [الحالة] لصالح العميل [الاسم]"*.
